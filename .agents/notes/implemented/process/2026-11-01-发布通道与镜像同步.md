# Agent Note: 发布通道与镜像同步

Status: implemented

## Problem

脚本此前只有一条分发路径：仓库里的文件，用户靠手动复制粘贴，或者使用 raw 链接。真实使用中发现三个后果：

- 用户想不起该发到哪个站点，也不清楚 Tampermonkey 的自动更新从哪来，每次发版都要重新解释一遍。
- 脚本头没有 `@updateURL` / `@downloadURL`，即使从 raw 地址安装，管理器也只能靠安装地址推断更新源。
- 目录整理后脚本路径从仓库根目录移到 `userscripts/<脚本>/`，老 raw 链接直接 404，而没有任何流程检查「发布地址上到底是哪个版本」。

## Decision

GitHub 是唯一真源，Greasy Fork 是镜像（站点没有自动同步能力，发版时手动上传一次），分发与更新都以此为准：

- 版本号唯一来源是脚本头的 `@version`，两个脚本各自演进；`package.json` 不参与发布判断。
- 脚本头的 `@updateURL` / `@downloadURL` 指向自己在 `userscripts/<脚本>/` 下的 raw 地址，由 `tests/versions.test.js` 校验它等于仓库中的真实路径。
- 新增 `npm run check-published`（`tools/check-published.js`），push 之后拉取 raw 地址并比对 `@version`，带重试以容忍 GitHub 的刷新延迟。
- 发版顺序固定为：改脚本 → 提 `@version` → `npm run archive-version` → `npm run check` + `npm test` → commit/push → `npm run check-published` → 在 Greasy Fork 的「更新」页粘贴或上传新代码并提交。
- 完整步骤、Greasy Fork 字段填写与排错写在 [`docs/发布流程.md`](../../../../docs/发布流程.md)。

## Alternatives considered

### Greasy Fork 作为主源，GitHub 只做镜像

能吃到 Greasy Fork 的搜索曝光，用户也能在站点内直接装。但 Greasy Fork 的代码编辑和版本管理能力弱于 git，历史版本、测试、文档、归档都需要另找地方；而且它会把脚本头里的更新地址接管成自己的，一旦以它为主源，仓库就只是副本，回滚和审计都失去可靠依据。

### 两个平台各自维护，互不同步

最省事，但两份代码必然分叉：改了 GitHub 忘了 Greasy Fork，用户装到哪个版本全凭运气，版本号也会出现同号不同内容。

### 只发 GitHub，不建镜像

可维护性最好，也是当前状态（`@updateURL` 已经够让管理器自动更新）。但用户明确需要「油猴脚本发布网址」这类入口来找脚本，GitHub 仓库没有脚本站的检索和安装体验，所以保留 Greasy Fork 作为镜像，代价只是发版时多一步同步。

## Consequences

收益：用户有两条可预期入口，安装后能自动更新；发版有固定清单，`check-published` 把「push 了但用户拿到旧版本」这种静默失败变成可检测的失败；版本号与归档、raw 路径由测试互相锁定。

代价：存在两条更新通道，GitHub 侧可自动校验，Greasy Fork 侧同步后仍需人工确认版本号；仓库路径一旦变动，Greasy Fork 的源码地址必须同步修改，否则镜像同步 404（本次目录整理就已经发生过一次）。发布流程比「改完直接 push」多了归档、校验、同步三步。

## Verification

- `npm run check-published` 对当前 `0.9.8` / `5.0.7` 返回「远程已是 0.9.8 / 5.0.7」，说明 raw 地址与本地一致。
- `tests/versions.test.js` 新增「每个脚本都声明指向发布路径的更新地址」：要求 `@updateURL` 与 `@downloadURL` 存在、彼此相等，且 `decodeURIComponent` 后等于 `raw 基址 + userscripts/<脚本>/<文件名>`。这条测试在本次实际拦下过一次漏写 `userscripts/` 前缀的错误。
- `npm run check` 与 `npm test`（20 项）通过。
